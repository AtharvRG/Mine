### 1. Guarantee Restatement
- **Guarantee 1 (Single Source of Truth)**: The `day_rule` table (`id`, `effective_from`, `start_minute`, `end_minute`, `tz_id`, `created_at`) is the sole authoritative source of truth for day boundaries and rollover timing across the entire system. Ad-hoc string settings like `day_start_minute` in `app_meta` or settings maps are eliminated.
- **Guarantee 2 (Effective Rule Resolution)**: At any given timestamp `ts`, the effective day rule is deterministically resolved by `SELECT * FROM day_rule WHERE effective_from <= ts ORDER BY effective_from DESC LIMIT 1`. If no row exists, a safe standard fallback (`startMinute = 240` [04:00], `endMinute = 1320` [22:00], `tzId = TimeZone.getDefault().id`) is returned.
- **Guarantee 3 (Next-Rollover Enforcement)**: Per Blueprint 50 s3.13, changes to day start or timezone take effect strictly at the **next rollover**, never mid-day. A day never splits or goes backwards. The `effective_from` of a newly scheduled rule is computed as the timestamp of the next day start under the current rule.
- **Guarantee 4 (Pure Helper & Monotonicity)**: A pure domain helper `DayRollover` resolves `day_key`, logical day start, and next rollover. `AndroidStorage.insertRawMessage` uses this helper and preserves strict `day_key` monotonicity bounded by tomorrow.

### 3. Diagnosis of Current Codebase Split

Currently, the codebase exhibits two diverging, uncoordinated sources of truth:
1. `AndroidStorage.insertRawMessage` queries the `day_rule` table directly in SQLite:
   ```kotlin
   dbHelper.readableDatabase.query("SELECT start_minute, tz_id FROM day_rule WHERE effective_from <= ? ORDER BY effective_from DESC LIMIT 1", arrayOf(ts))
   ```
   and duplicates timezone offset arithmetic, rollover subtraction, and date formatting inline.
2. `Gateway.propose_change` (lines 128 & 243) and `CheckinBuilder.buildMorningFacts` (line 17) query:
   ```kotlin
   val rolloverMin = storage.getSetting("day_start_minute")?.toIntOrNull() ?: 240
   ```
   which reads from `app_meta` or in-memory settings, completely oblivious to `day_rule`, `effective_from`, and timezone history!
3. `SharedFakeStorage` has no `day_rule` state or contract implementation at all.
4. There is no helper to calculate when the next rollover occurs or schedule a new rule without breaking the current day.

### 4. Architecture: The Single Source of Truth

#### 4.1 Data Model
In `core/src/main/java/com/anchor/core/models/Memory.kt`:
```kotlin
@Serializable
data class DayRule(
    val id: String,
    val effectiveFrom: Long,
    val startMinute: Int,
    val endMinute: Int = 1320,
    val tzId: String,
    val createdAt: Long
)
```

#### 4.2 Core Pure Helper `DayRollover`
In `core/src/main/java/com/anchor/core/time/DayRollover.kt`:
- `computeDayKey(tsUtc: Long, rule: DayRule): String`:
  Computes the `YYYY-MM-DD` string corresponding to the logical date in the rule's timezone.
- `getLogicalDayStart(tsUtc: Long, rule: DayRule): Long`:
  Returns the exact UTC timestamp when the logical day began.
- `getNextRollover(nowUtc: Long, currentRule: DayRule, targetTzId: String? = null, targetStartMinute: Int? = null): Long`:
  Calculates the exact timestamp of the upcoming rollover boundary. If changing timezone or start minute, computes the boundary per Blueprint 50 s3.13.
- `scheduleNextRule(currentRule: DayRule, newStartMinute: Int, newEndMinute: Int, newTzId: String, nowUtc: Long): DayRule`:
  Constructs a new `DayRule` with `effectiveFrom = getNextRollover(...)` and `createdAt = nowUtc`.

#### 4.3 Storage Contract
In `core/src/main/java/com/anchor/core/storage/Storage.kt`:
```kotlin
suspend fun getEffectiveDayRule(tsUtc: Long): DayRule
suspend fun saveDayRule(rule: DayRule)
```

#### 4.4 Storage Implementations
- `AndroidStorage.kt`:
  Queries SQLite `day_rule` with parameterized `effective_from <= ? ORDER BY effective_from DESC LIMIT 1`. Saves via `INSERT OR REPLACE INTO day_rule`. `insertRawMessage` delegates date math to `DayRollover.computeDayKey`.
- `SharedFakeStorage.kt`:
  Maintains in-memory `List<DayRule>`, sorting by `effectiveFrom DESC`, filtering by `effectiveFrom <= tsUtc`.

#### 4.5 Consumers Re-Wired
- `Gateway.propose_change`:
  Reads `storage.getEffectiveDayRule(clock.now()).startMinute` instead of `getSetting("day_start_minute")`.
- `Gateway.handleScheduleReminder`:
  Reads `storage.getEffectiveDayRule(clock.now()).startMinute`.
- `CheckinBuilder.buildMorningFacts`:
  Reads `storage.getEffectiveDayRule(now)`. Passes `rule.startMinute` to `getLogicalDayStart`.

### 5. Hypothesis Table & Failure Modes

| Hypothesis | Test / Verification | Expected Outcome |
| :--- | :--- | :--- |
| **H1: Changing day_start mid-day does not alter current day's messages or proposals** | Save rule at 14:00 with start 06:00 -> 08:00. Query `getEffectiveDayRule(14:00)`. | Returns previous rule. Returns new rule only at/after next day's 04:00/06:00 rollover. |
| **H2: Late night messages belong to previous day** | Message at 02:00 with 04:00 day start. | `day_key` matches previous calendar date. |
| **H3: Timezone change takes effect at next day start in new zone** | Change timezone from UTC to Tokyo (+9h) at 12:00 UTC. | Next rollover is computed in new timezone, taking effect at next boundary without splitting today. |
| **H4: Clock skew or backward step does not break monotonicity** | Message 2 is timestamped before Message 1. | `day_key` is strictly `>=` previous message `day_key`. |
| **H5: Empty table safe fallback** | DB with 0 `day_rule` rows. | Returns default rule (`startMinute = 240`, `tzId = device default`), no crashes. |

### 6. Pre-Mortem
- **Risk**: What if `TimeZone.getTimeZone(rule.tzId)` fails on invalid string?
  - *Mitigation*: Fall back to `TimeZone.getDefault()` if `TimeZone.getAvailableIDs().contains(rule.tzId)` is false or if `getTimeZone` returns GMT for a non-GMT unrecognized string.
- **Risk**: What if `effectiveFrom` calculation under DST shifts by 1 hour?
  - *Mitigation*: Use `Calendar` initialized with the rule's specific `TimeZone` and adjust day-of-year so Java/Android calendar automatically applies local DST rules at the target date.
