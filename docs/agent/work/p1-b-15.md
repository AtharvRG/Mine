# P1-B 15 Branching Analysis: Reminder Policy per Blueprint 30 (Lead Times, Reminder Only When Asked or Per Default)

## A. Goal and Invariant
- **Goal**: Implement the reminder policy specified in Blueprint 30 (sections 3.1, 3.2, 3.3, 3.4, 3.9) and Blueprint 52 line 174:
  1. **Creation Policy (s3.1, s3.3, D-035)**: Explicit user temporal commands create reminders by default (lead time = 0 at `dueAt` for dated tasks); undated items create no alarms; AI-inferred reminders follow setting `reminder.ai_suggest` (`ask` default with chips: `[Set <time>]`, `[Change]`, `[No]`; `auto` creates with Undo).
  2. **Lead Times & Vague Day-Parts (s3.4)**: Resolves vague day-part phrases ("morning", "afternoon", "evening", "night", "soon", "later") using defined time windows and node severity (sev 3 = 10% into window, sev 2 = 35%, sev 1 = 60%, sev 0 = 75%). Supports relative lead time offsets (`offset_text` or relative expressions e.g. "15 minutes before", "1 hour before") anchored to `node.dueAt`.
  3. **Duplicate Reminder Policy (s3.3)**: If a reminder for the same node already exists within 30 minutes (`Math.abs(existing.fireAtMillis - fireAt) <= 30 * 60 * 1000L`), `schedule_reminder` returns `ToolResult.NeedsConfirm` ("A reminder is already set for <existing>. Update it, or cancel?") with options to update or cancel instead of silently overwriting.
  4. **Quiet Hours / Day Window Policy (s3.3, D-035)**: Explicit user reminders ring even outside the day window (requested-class). AI-suggested or auto-created reminders outside the active day window (`startMinute..endMinute`) are moved to `day_start + 30 min`.
- **Invariant**:
  - Code decides, model proposes (Rule 1).
  - Explicit reminders ring when requested, even in quiet hours (D-035, s3.1).
  - Vague temporal phrases resolve deterministically to exact timestamps without model guessing (Rule 4, s3.4).
  - Reminders on the same node within 30 minutes are never silently duplicated or destroyed without user confirmation (s3.3).
  - No changes without raw_event logging and undoability (Rule 3).

## C. Angles (one line each, mandatory)
- **data/schema**: No schema migration required; `setting` table stores `reminder.ai_suggest`; `reminder` and `proposal` tables support required fields.
- **concurrency/lifecycle**: CAS concurrency and transactional CAS (D-118) protect confirmation of duplicate reminder updates.
- **failure paths**: Missing node on relative offset returns immediate error; past calculated time returns "That time has already passed; tell me a future time."
- **what a REAL model would send**: Real LLM emits `schedule_reminder` with `when_text`, `offset_text`, `target_ref`, and `inferred=true` or calls `propose_change CREATE`.
- **user-visible behaviour**: Vague phrases ("this evening", "soon", "later") echo exact computed clock times; near-duplicate reminders prompt with chips; explicit alarms ring even in quiet hours.
- **privacy and security**: No sensitive data in raw events; zero-vibration protocol strictly preserved; no new permissions required.
- **testability**: Deterministic unit tests in `:core` using `FakeClock` and `SharedFakeStorage` for all day-part windows, severities, lead times, duplicates, and quiet hours.
- **battery and performance**: O(1) calculations in `DateResolver` and `Gateway`; no background polling or extra threads.
- **blast radius**: Confined to `DateResolver.kt`, `Gateway.kt`, and `ContextBuilder.kt` / prompt instructions.

## D. Discriminating Checks
1. Check `dateResolver.resolve` with day-parts and severities:
   - "morning" with sev 3 -> 07:24; sev 2 -> 08:24; sev 1 -> 09:24; sev 0 -> 10:00.
   - "evening" with sev 2 -> 18:03 (or 17:35 if 35-min offset); sev 0 -> 19:15.
   - "soon" -> now + 30m; "later" -> now + 2h.
2. Check relative offset:
   - Node due at 17:00, `offset_text = "30 minutes before"` -> fires at 16:30.
3. Check 30-minute duplicate check:
   - Reminder at 17:00, new reminder at 17:15 -> returns `NeedsConfirm`.
   - Reminder at 17:00, new reminder at 18:00 -> succeeds directly (>30 min).
4. Check quiet hours:
   - Inferred reminder at 02:00 -> adjusted to 04:30 (4:00 + 30 min).
   - Explicit reminder at 02:00 -> remains at 02:00.

## E. Chosen Change and Rejected Options
- **Chosen**:
  1. In `DateResolver.kt`:
     - Add `severity: Int? = null` parameter to `resolve()`.
     - Implement window plus severity resolution for "morning" (07:00..11:00), "afternoon" (12:00..16:00), "evening" (17:00..20:00), "night" (20:00..23:00) per s3.4:
       `offsetMinutes = windowDurationMinutes * percent / 100` where percent is 10 (sev 3), 35 (sev 2), 60 (sev 1), 75 (sev 0).
     - Add support for "soon" (`now + 30 min`) and "later" (`now + 2 hours` clamped to day end) per s3.4.
     - Add support for "N min/hours before" relative duration parsing.
  2. In `Gateway.kt`:
     - Pass `severity` to `dateResolver.resolve`.
     - In `handleScheduleReminder`:
       - Support `offset_text` or relative "before" offsets anchored to `node.dueAt`.
       - Check duplicate reminders for the same node within 30 minutes (`Math.abs(existing.fireAtMillis - fireAt) <= 30 * 60 * 1000L`); if found, issue `ToolResult.NeedsConfirm` with `[Update existing, Cancel]`.
       - Check quiet hours: if `inferred == true` and `fireAt` is outside `dayRule.startMinute..dayRule.endMinute`, adjust to `day_start + 30 min`.
       - Check `reminder.ai_suggest` setting when `inferred == true`; if `ask` (default), return `NeedsConfirm` with chips `[Set <time>, Change, No]`.
     - In `handleConfirmChange`:
       - Handle `schedule_reminder` duplicate confirmation (`update` updates existing reminder; `cancel` consumes proposal).
  3. Document choice in `docs/agent/DECISIONS.md` as D-120 citing Blueprint 30 sections 3.1, 3.2, 3.3, 3.4, 3.9.
- **Rejected**:
  - Auto-creating reminders on undated tasks: rejected because undated tasks have no temporal intention (s3.1).
  - Silently overwriting reminders within 30 minutes: rejected because s3.3 mandates asking to update.
  - Moving explicit user reminders into quiet hours: rejected because D-035 and s3.3 explicitly mandate that user commands ring anyway.

## F. Pre-Mortem (3 Potential Failure Modes)
1. *Failure*: User says "remind me at 9" without specifying morning or evening.
   *Defense*: D-103 bare hour ambiguity returns `NeedsClarification` with chips (09:00 / 21:00), never guessing.
2. *Failure*: Task due date is moved or cancelled, but reminder remains orphaned.
   *Defense*: D-100 and D-110 mandate that node cancellation cancels attached reminders; reschedule updates attached reminder.
3. *Failure*: Rapid concurrent confirmations on duplicate reminder update.
   *Defense*: In-transaction proposal CAS (D-118) ensures single-winner semantics and rollback for losing taps.

## G. Questions & Ambiguities
- The choices required by line 23 of ROADMAP.md are fully specified by Blueprint 30:
  - Lead times: relative offset via `offset_text` / "before" phrases anchored to `dueAt`; vague day-parts positioned via severity percentage into window; default lead time = 0 (at `dueAt`).
  - Reminder creation: per default for dated tasks/intentions, only when asked for undated items; AI-inferred reminders governed by `reminder.ai_suggest` (`ask` default vs `auto`).
  - Documented as Decision D-120 citing Blueprint 30 sections 3.1, 3.2, 3.3, 3.4, 3.9.
