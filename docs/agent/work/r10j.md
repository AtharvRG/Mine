### 1. Goal and Invariant Restatement
- **Goal**:
  Per `docs/agent/TASKS.md` line 61 and `session1-remediation-spec.md` line 316 (also citing Part 1 Section C, Item 1 in `session2_user_prompt.txt`):
  > "R10j Chat history search indexing: populate msg_chunk_fts on message insert so searchMemoryFts searches conversation history"
- **Invariants**:
  1. *FTS External Content Sync*: `msg_chunk` is the external content table for `msg_chunk_fts` (`content='msg_chunk', content_rowid='rowid'`). Triggers (`trg_msg_chunk_fts_insert`, `trg_msg_chunk_fts_delete`, `trg_msg_chunk_fts_update`) must keep `msg_chunk_fts` in strict sync with `msg_chunk`.
  2. *Message Insertion Atomicity*: Inserting a conversation message (`raw_message`) must populate a corresponding `msg_chunk` row atomically in the same database transaction. Non-blank `user` and `assistant` messages are indexed; `system` messages are excluded.
  3. *Redaction Scrubbing*: When `redactMessage(id)` deletes the associated `msg_chunk` row via `msg_ids LIKE '%"$id"%'`, the `AFTER DELETE` trigger on `msg_chunk` must remove the entry from `msg_chunk_fts`, ensuring zero text leakage.
  4. *Search Unification*: `searchMemoryFts(query, limit)` must query `node_fts`, `soul_fts`, and `msg_chunk_fts`, returning unified `SearchResult` objects with `kind = "chat"`, `title = day_key`, and `details = text`.
  5. *Storage Parity*: `SharedFakeStorage` must mirror this search behavior for deterministic unit testing in `:core`.

### 2. Hypotheses / Approaches

1. **Hypothesis A: Separate background indexing worker / job**:
   - *Description*: Insert messages into `raw_message` only, and run a periodic coroutine or background job to chunk and index messages into `msg_chunk`.
   - *Kill Condition*: Asynchronous lag breaks immediate search testability ("insert message -> search memory immediately finds it"). Overengineers a simple operation with concurrency overhead.

2. **Hypothesis B: Single-message 1:1 chunking in `insertRawMessage` with FTS sync triggers** (CHOSEN):
   - *Description*:
     - In `MineDatabaseHelper.createTriggers(db)`: Add `trg_msg_chunk_fts_insert`, `trg_msg_chunk_fts_delete`, and `trg_msg_chunk_fts_update` matching the standard SQLite FTS5 external content sync pattern used for `node_fts` and `soul_fts`.
     - In `AndroidStorage.insertRawMessage`: Within the write transaction, if `content.isNotBlank() && role != "system"`, insert a row into `msg_chunk` with `id = "chunk_$id"`, `day_key = dayKey`, `ts_start = ts`, `ts_end = ts`, `msg_ids = "[\"$id\"]"`, `text = content`, and `extractor_version = "v1"`.
     - In `AndroidStorage.searchMemoryFts`: Query `msg_chunk JOIN msg_chunk_fts ON msg_chunk.rowid = msg_chunk_fts.rowid WHERE msg_chunk_fts MATCH ? ORDER BY msg_chunk_fts.rank LIMIT ?` and map matches to `SearchResult(id, "chat", dayKey, text)`.
     - In `SharedFakeStorage.searchMemoryFts`: Filter non-null, non-system messages containing the query, returning `SearchResult("chunk_${it.id}", "chat", it.dayKey ?: "", it.content!!)`.
   - *Prediction*: Immediate consistency, zero lag, automatic deletion upon redaction (via existing `DELETE FROM msg_chunk WHERE msg_ids LIKE '%"$id"%'`), full unit and connected testability.

3. **Hypothesis C: Multi-message sliding window chunking**:
   - *Description*: Combine multiple messages within a day into multi-turn chunks.
   - *Kill Condition*: Substantially higher complexity, complicates single-message redaction (redacting one message would require re-chunking and re-indexing neighboring messages), and violates the instruction to not overengineer.

### 3. Comprehensive Dimensional Analysis
- **Schema & Migration**: Tables `msg_chunk` and `msg_chunk_fts` are already present in DB v5. Adding sync triggers in `createTriggers(db)` requires no schema version bump, as `createTriggers` is executed on both `onCreate` and `onUpgrade`.
- **Concurrency & Transactionality**: `AndroidStorage.insertRawMessage` wraps `raw_message` insert and `msg_chunk` insert in a single `db.beginTransaction() ... db.setTransactionSuccessful()` block.
- **Process Death & Reboot**: Fully persisted to disk inside SQLite; survives app kills and reboots.
- **Privacy & Redaction**: When a message is redacted via `AndroidStorage.redactMessage`, the existing SQL `DELETE FROM msg_chunk WHERE msg_ids LIKE ?` deletes the `msg_chunk` row. The `AFTER DELETE` trigger on `msg_chunk` (`trg_msg_chunk_fts_delete`) scrubs the FTS index immediately.
- **Model / Tool Contract**: Tool `search_memory` returns lines formatted `${it.id} | ${it.kind} | ${it.title} | ${it.details}`. A chat result appears as `chunk_m1 | chat | 2026-11-04 | Remember to bring the umbrella`, providing clear chronological context to the LLM.
- **Blast Radius**: `MineDatabaseHelper.kt`, `AndroidStorage.kt`, `SharedFakeStorage.kt`, and test suites in `:core` and `:app`.

### 4. Pre-Mortem (3 Potential Failure Modes)
1. *FTS Triggers missing on pre-existing database*: If a database was opened without running trigger creation, `msg_chunk_fts` would not receive insert events.
   - *Mitigation*: Ensure `createTriggers(db)` includes `CREATE TRIGGER IF NOT EXISTS` for all three `msg_chunk_fts` triggers, and is invoked in `onCreate` and `onUpgrade`.
2. *Redaction fails to delete chunk due to ID format mismatch*: `redactMessage` uses `WHERE msg_ids LIKE '%"$id"%'`.
   - *Mitigation*: Format `msg_ids` as `[\"$id\"]` so the quoted ID is guaranteed to match `%"$id"%`.
3. *System prompt / instructions indexed*: System messages contain static instructions that could pollute memory search.
   - *Mitigation*: Guard `insertRawMessage` with `if (content.isNotBlank() && role != "system")`.
