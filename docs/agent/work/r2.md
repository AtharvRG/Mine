# R2 Branching Analysis: Candidate Selection & 100-Item Default Remediation

## 1. Problem Analysis
In the current implementation, `Storage.getActiveNodes(limit: Int = 100, cursor: String? = null, order: String = "ASC")` defaulted to `limit = 100`. Multiple critical subsystems relied on this default:
1. `Gateway.handleResolveChange`: fetched candidates using `storage.getActiveNodes()`. With >100 active items, any candidate ranked past position 100 (e.g. item #250 by due date) was invisible to `Resolver`, resulting in unexpected `NotFound` errors (e.g., "cancel dinner" failing).
2. `Gateway` CREATE duplicate title check: fetched `storage.getActiveNodes()` and checked for title matches. If the matching title was beyond the first 100 nodes, duplicate detection failed, creating duplicate active items.
3. `CheckinBuilder.buildMorningFacts`: loaded `storage.getActiveNodes()` to count today's and overdue items. With >100 nodes, counts and agenda were truncated and factually wrong.
4. `ContextBuilder.buildPack`: called `storage.getActiveNodes(limit = 100)`, filtered stale items in Kotlin, and ranked the remainder. If 100 stale overdue items existed, all 100 items were discarded in memory, resulting in an empty prompt context even when fresh active items existed. Furthermore, undated pinned and high-severity items sorted after all dated items, meaning 150 future dated items would starve pinned or severity>0 items from ever reaching the ranking pool.

## 2. Call Site Audit for `getActiveNodes`
Current call sites across the codebase:
- `core/src/main/java/com/anchor/core/gateway/Gateway.kt`:
  - Line 113: CREATE duplicate check -> replace with `storage.findActiveNodeByTitle(title)`.
  - Line 263: Resolver candidate retrieval -> replace with `storage.getAllActiveNodesPaged(pageSize = 200, hardCap = 5000)`.

- `core/src/main/java/com/anchor/core/context/ContextBuilder.kt`:
  - Line 31: Context candidate retrieval -> replace with `storage.getRankedCandidates(now, staleCutoffMs, perTierLimit = 25)`.

## 3. Storage Interface Changes
In `Storage.kt`:
1. `getActiveNodes(limit: Int, cursor: String? = null): List<Node>`:
   - Make `limit` a required parameter (no default).
   - Remove unused and unhonored `order` parameter (always uses canonical keyset ordering `due_at IS NULL, due_at ASC, id ASC`).
2. `getAllActiveNodesPaged(pageSize: Int = 200, hardCap: Int = 5000): List<Node>`:
   - Core extension or Storage method that pages using keyset cursor up to `hardCap`.
   - If `hardCap` is exceeded, throws `TooManyActiveNodesException(cap)`.
3. `findActiveNodeByTitle(title: String): Node?`:
   - Case-insensitive on ASCII, trimmed title match on active nodes (`status IN ('active', 'in_progress', 'paused')`).
4. `getNodesDueBetween(startMs: Long, endMs: Long, limit: Int): List<Node>`:
   - Returns active nodes with `due_at >= startMs AND due_at < endMs` ordered by `due_at ASC, id ASC LIMIT limit`.
5. `getOverdueNodes(beforeMs: Long, limit: Int): List<Node>`:
   - Returns active nodes with `due_at < beforeMs` ordered by `due_at ASC, id ASC LIMIT limit`.
6. `getRankedCandidates(now: Long, staleCutoffMs: Long, perTierLimit: Int = 25): List<Node>`:
   - Queries 6 tiers in SQL excluding stale items (`created_at = 0 OR max(updated_at, created_at) >= now - staleCutoffMs`):
     - Tier 1: Overdue (`due_at IS NOT NULL AND due_at < now`, order by `due_at ASC, id ASC`)
     - Tier 2: In progress (`status = 'in_progress'`, order by `due_at IS NULL, due_at ASC, severity DESC, recency DESC, id ASC`)
     - Tier 3: Due within 48h (`due_at >= now AND due_at <= now + 48h`, order by `due_at ASC, id ASC`)
     - Tier 4: Pinned (`pinned = true`, order by `severity DESC, recency DESC, id ASC`)
     - Tier 5: Severity (`severity > 0`, order by `severity DESC, recency DESC, id ASC`)
     - Tier 6: Recency (order by `recency DESC, id ASC`)
   - Returns distinct union of candidates.

## 4. Architectural & Safety Decisions
- **D-113**: Paged candidate resolution hard cap. In `Gateway.handleResolveChange`, `getAllActiveNodesPaged` caps at 5,000 nodes. If the user has more than 5,000 active nodes, return `ToolResult.Error("Too many active items (exceeded 5000). Please be more specific.")` rather than silently operating on a partial dataset.
- **SQL-Level Stale Filtering**: `ContextBuilder` no longer fetches 100 nodes and filters stale items in Kotlin. The 6-tier queries in `AndroidStorage.getRankedCandidates` enforce non-stale filtering in SQLite via `(created_at = 0 OR (CASE WHEN updated_at > 0 THEN updated_at ELSE created_at END) >= ?)`.
