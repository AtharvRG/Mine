# Task R4: Unreachable Features: Stale Items and Time Chips (T-A, T-B)

Date: 2026-11-04  
Status: Completed / Verified  
Author: Antigravity / OpenClaude

## 1. Context & Objectives

Remediation Task R4 addresses features that were implemented in storage or resolver but remained unreachable in practice:
1. **Stale Items Surfacing**: Nodes inactive for 30+ days were filtered out of the AI context pack (D-104) but never displayed anywhere to the user (`getStaleNodes` was only invoked by unit tests).
2. **Time Clarification Chips**: `DateResolver.resolve()` returns `NeedsClarification` for ambiguous times (e.g. bare "at 5" without AM/PM per D-103), but `Gateway` called only `dateResolver.parse()`, which returns null. The AI received "Could not understand the time", forcing redundant model reprompting and never presenting clarification chips.
3. **DateResolver Ambiguities & Edge Cases**:
   - "N at night" and "tonight at 1..5" mapped erroneously to 13:00..17:00 (afternoon).
   - "12 in the evening" and "12 in the afternoon" had unnatural or invalid mappings.
   - Weekday expressions ("on friday", "next friday", "friday at 5pm") were missing.
   - Chip labels were hardcoded to 24h format (`%02d:%02d`) even on 12h devices.

## 2. Architecture & Design

### A. Stale Items Protocol
- **UI State & Actions**:
  - `UiState.staleItems: List<Node>`
  - `UiState.inboxCount = openProposals.size + proposedSoulFacts.size + staleItems.size`
  - `UiAction.KeepStale(nodeId: String)`: Touches `updatedAt` to `clock.now()` through an undoable transactional commit (`KEEP_STALE`), restoring the node to the active context pool and removing it from the stale list.
  - `UiAction.CancelStale(nodeId: String)`: Transitions node to `cancelled` and removes any pending reminder through an undoable transactional commit (`CANCEL_STALE`).
- **Core Placement**: Logic lives in `Gateway.handleKeepStale` and `Gateway.handleCancelStale`, not in UI controllers. Both generate `RawEvent` records with `NodeStateSnapshot` before/after JSON for full 24h undo support.

### B. Time Chips Protocol (D-110 Zero-Model-Call Flow)
- **Resolver Integration**:
  - `Gateway` invokes `dateResolver.resolve(dueText, rolloverMin)` instead of `parse()`.
  - For `CREATE` and `RESCHEDULE`, if resolution returns `DateResolution.NeedsClarification`:
    - Create a `Proposal` with `kind = "time"` and `status = "open"`.
    - Options: Candidate times with `id = timeMillis.toString()`, `title = dateResolver.formatTimeOnly(timeMillis)`.
    - Payload (`ProposalPayload`): Carries `intent`, `title`, `type`, `followUpTo`, `tier`, `hint`, `priority`, `severity`, `pinned`.
    - Return `ToolResult.NeedsTime(proposalId, chipLabels)`.
  - `ChatController` ends the turn upon `NeedsTime` (like `Ambiguous`), exposing options to `UiState.openProposals`.
- **Zero-Model-Call Confirmation**:
  - `UiAction.ConfirmProposal(proposalId, choiceId)` calls `Gateway.handleConfirmChange`.
  - If `proposal.kind == "time"`:
    - Decode `chosenMillis = choiceId.toLong()`.
    - Validate `chosenMillis > clock.now()`; if expired, consume proposal and return explicit error.
    - If `intent == CREATE`: Execute node + reminder creation at `chosenMillis`.
    - If `intent == RESCHEDULE`: If target node is known, reschedule immediately; if target was ambiguous, proceed to target resolution with `destinationTimeMillis = chosenMillis`.
    - Consumes proposal atomically in SQLite transaction.
    - Emits deterministic receipt with undo token. Zero model round-trips.
- **Cancel / Complete Ambiguity**:
  - For `CANCEL` and `COMPLETE`, an ambiguous `due_text` is ignored as an identifier (`timeForResolver = null`), resolving solely by title/hint.

### C. DateResolver Enhancements
1. **Unnatural Hour Mappings**:
   - Hours 1..5 with "night" or "tonight at 1..5": Return `NeedsClarification` (01:00 vs 13:00 / 03:00 vs 15:00).
   - "12 in the evening" and "12 in the afternoon": Return `NeedsClarification` (00:00 vs 12:00).
   - Hours 6..11 with "night" or "tonight": Unambiguous PM (18:00..23:00).
   - "12 at night": Unambiguous 00:00 next calendar day.
2. **Weekday Names**:
   - Parses "on <weekday>", "next <weekday>", "<weekday> [at <time>]".
   - Default time without time part: 09:00 AM on that target weekday.
   - If time part is ambiguous ("friday at 5"), returns `NeedsClarification` for that weekday.
3. **Device Time Formatting**:
   - `formatTimeOnly(timeMillis: Long)`: Respects `is24HourFormat` ("HH:mm" vs "h:mm a").
   - `chipLabels` use `formatTimeOnly` instead of hardcoded 24h string.

## 3. Branching Analysis & Invariants

| Action / State | Condition | Outcome | Undoable |
| :--- | :--- | :--- | :--- |
| `CREATE` with "at 5" | `NeedsClarification` | `Proposal(kind="time")`, `ToolResult.NeedsTime` | Yes (upon confirm) |
| Tap time chip | `chosenMillis > clock.now()` | Node created, 1 reminder armed, proposal consumed | Yes (`handleUndo`) |
| Tap time chip | `chosenMillis <= clock.now()` | Error returned, proposal consumed | No mutation |
| `RESCHEDULE` with "at 5" + ambiguous target | Time ambiguous first | Time chips presented $\to$ Target chips presented $\to$ Rescheduled | Yes |
| `CANCEL` with "at 5" | Ambiguous time in due_text | Time ignored; resolved by title text | Yes |
| `KeepStale(id)` | Node idle >30 days | `updatedAt` updated to now; leaves stale list | Yes (`handleUndo`) |
| `CancelStale(id)` | Node idle >30 days | `status="cancelled"`, reminder cancelled | Yes (`handleUndo`) |
