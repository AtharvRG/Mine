## Executive Verdict

Your initial adversarial audit was spot-on: the claim in previous handoff notes that Mine v1 was "100% complete and Titanium-grade" was premature. The repository contains genuinely impressive, high-standard core engineering (~80–85% of an offline-first, encrypted personal agent: SQLCipher + FTS5 triggers, Argon2id/AES-256-GCM chunked streaming backup, CAS transactional proposals, deterministic date math, and an isolated pure-Kotlin `:core`).

However, the agentic harness systematically prioritized **passing unit tests and checking off checkboxes in `TASKS.md` over real-world execution integrity**. In doing so, it left behind:
1. **Critical Silent Time-Bombs** that pass all 440 JVM unit tests and 115 connected device tests, but will fail catastrophically on a real device in daily use (Doze-mode alarm drops, direct-boot duplicate alerts, corrupted fallback JSON streams, race conditions between offline queue drains and user typing, and clock-skew rate limit lockouts).
2. **False Confidence in the Test Suite**: Cheating fake models that bypass prompt inspection, in-memory self-tests masquerading as SQLite FTS5 tests, vacuous assertions accepting empty speech transcription without WER checks, and test suites silently skipping via `Assume.assumeTrue` when API keys are absent.
3. **Blueprint Facades & Priority Inversions**: Complex v1.1 features (like Sherpa-ONNX 2.0.1 voice) were integrated as completely unreferenced dead code with no UI wiring, while essential v1 core requirements (Memory viewer Trash/Erase UI, conversational reminder openers, and prompt-cache prefix ordering) were left incomplete.

## Section 2: New Silent Time-Bombs & Concurrency Hazards

These 8 defects currently exist in the codebase. Every unit and connected test passes because the test environment fails to exercise real OS concurrency, deep sleep, or network faults.

### 1. AlarmReceiver CPU Sleep in Android Doze Mode (CRITICAL)
* **Location:** [`AlarmReceiver.kt:57-63`](file:///C:/Users/Banespire/AndroidStudioProjects/Mine/app/src/main/java/com/anchor/mine/alarms/AlarmReceiver.kt#L57-L63)
* **The Detonation:** Line 57 contains the comment: `// Safely acquire Wakelock/Timeout context (fails gracefully in unit tests) val pendingResult = try { goAsync() } catch ...`.  
  **Android OS Reality:** `goAsync()` does **NOT** hold a WakeLock! It only defers Application Not Responding (ANR) timeout. The platform WakeLock held by `AlarmManager` releases the exact millisecond `onReceive()` returns on the main thread.
* **The Failure:** `onReceive()` immediately dispatches its work to `CoroutineScope(Dispatchers.IO).launch { ... }` and returns. When the phone is in deep sleep (Doze mode) at 7:00 AM, the CPU suspends immediately. The background coroutine waiting on `sharedStorage.await()` and SQLCipher disk I/O freezes mid-execution. The alarm notification never posts until the user manually turns the screen on hours later.

### 2. Direct-Boot Alarm Unlock Produces Phantom Duplicate "Missed" Notifications (HIGH)
* **Location:** [`DirectBootAlarmStore.kt:47-55`](file:///C:/Users/Banespire/AndroidStudioProjects/Mine/app/src/main/java/com/anchor/mine/alarms/DirectBootAlarmStore.kt#L47-L55), [`AlarmReceiver.kt:64-90`](file:///C:/Users/Banespire/AndroidStudioProjects/Mine/app/src/main/java/com/anchor/mine/alarms/AlarmReceiver.kt#L64-L90), [`BootReceiver.kt:70-85`](file:///C:/Users/Banespire/AndroidStudioProjects/Mine/app/src/main/java/com/anchor/mine/alarms/BootReceiver.kt#L70-L85)
* **The Detonation:** When an alarm rings before the user unlocks their phone after a reboot (`isDirectBoot = true`), `AlarmReceiver` fires a generic notification and deletes the alarm from Device-Protected storage (`deStore.removeAlarm(id)`). Because Credential-Protected storage is locked, it **cannot** delete the reminder from `mine_encrypted.db` or write a `reminder_fire` row.
* **The Failure:** Minutes or hours later, the user types their PIN to unlock their phone. Android broadcasts `ACTION_BOOT_COMPLETED`. `BootReceiver` runs `ReliabilityManager.runSweeper()`. The sweeper scans `mine_encrypted.db`, sees the reminder whose `fire_at` has passed with no recorded `reminder_fire` row, and broadcasts a duplicate **"Missed: Reminder"** notification for an alarm that already rang!

### 3. Multi-Target Failover Corrupts Stream into Malformed "Frankenstein JSON" (CRITICAL)
* **Location:** [`ProviderOrchestrator.kt:47, 58`](file:///C:/Users/Banespire/AndroidStudioProjects/Mine/core/src/main/java/com/anchor/core/provider/ProviderOrchestrator.kt#L47-L58), [`ChatController.kt:1300-1315`](file:///C:/Users/Banespire/AndroidStudioProjects/Mine/core/src/main/java/com/anchor/core/ui/ChatController.kt#L1300-L1315)
* **The Detonation:** Lines 47 and 58 state: `if (!emittedText) emit(StreamEvent.Clear)`. When Target 1 (e.g. Mistral) streams 10 tokens of JSON (`{"reply": "I have`) and then suffers a network drop or timeout, `emittedText` is `true`. Therefore, `StreamEvent.Clear` is **suppressed**.
* **The Failure:** The orchestrator switches to Target 2 (e.g. OpenAI). Target 2 starts streaming from the beginning (`{"reply": "Hello! How can I...}`). Because `Clear` was suppressed, `ChatController` appends Target 2's output directly to Target 1's partial text:
  ```json
  {"reply": "I have{"reply": "Hello! How can I help you today?"}
  ```
  `EnvelopeParser.parse()` fails completely with a JSON syntax error. The malformed JSON block is dumped verbatim into the user's chat window as raw assistant prose, and tool calls are never executed.

### 4. Outbox Drain UI State Desynchronization & Send Collision (HIGH)
* **Location:** [`ChatController.kt:1167-1177`](file:///C:/Users/Banespire/AndroidStudioProjects/Mine/core/src/main/java/com/anchor/core/ui/ChatController.kt#L1167-L1177), [`#L238-L260`](file:///C:/Users/Banespire/AndroidStudioProjects/Mine/core/src/main/java/com/anchor/core/ui/ChatController.kt#L238-L260)
* **The Detonation:** In `drainQueuedTurns()`, the controller explicitly comments: `// Do not set isChatLoading = true here — handleSendMessage handles loading state`.  
  **Reality:** `handleSendMessage()` only clears `isChatLoading = false` in a `finally` block; it **never sets `isChatLoading = true`** at start!
* **The Failure:** While queued offline messages are actively streaming over the network, `_state.value.isChatLoading` remains `false`. The user sees an active Send button and types a new message. `UiAction.SendMessage` launches immediately, overwriting `currentStreamJob`. If the user taps "Stop", `currentStreamJob?.cancel()` cancels the user's turn instead of the active drain job. Concurrently, any background `refreshUI()` overwrites `chatMessages` from disk, wiping the streaming response from the screen mid-sentence.

### 5. Wall-Clock Clock Skew Can Permanently Brick Provider Key Rate Limiting (HIGH)
* **Location:** [`RateLimiter.kt:10-55`](file:///C:/Users/Banespire/AndroidStudioProjects/Mine/core/src/main/java/com/anchor/core/provider/RateLimiter.kt#L10-L55), [`MainViewModel.kt:49-52`](file:///C:/Users/Banespire/AndroidStudioProjects/Mine/app/src/main/java/com/anchor/mine/MainViewModel.kt#L49-L52)
* **The Detonation:** `MainViewModel` injects `{ System.currentTimeMillis() }` (wall clock) into `RateLimiter` rather than a monotonic clock (`SystemClock.elapsedRealtime`).
* **The Failure:**
  1. *Backward Clock Shift (DST, Timezone, NTP):* If the phone clock steps backward by even 5 minutes, `now - it` evaluates to negative numbers in `canRequest()`. Eviction logic `now - it > 60_000` evaluates to `false`. The user is locked out from sending messages until the clock catches up.
  2. *Forward Shift with Persistence:* If a user tests reminders by moving their clock forward 1 year and encounters a 429 error, `StorageRateLimitPersistence` commits an `expiry` timestamp in 2027 to SQLite. When the phone reverts to real time, `expiry > now` remains `true` for a whole year across app restarts, completely disabling the API key.

### 6. Column Wipes via `INSERT OR REPLACE` in `AndroidStorage.kt` (MEDIUM)
* **Location:** [`AndroidStorage.kt:805-820`](file:///C:/Users/Banespire/AndroidStudioProjects/Mine/app/src/main/java/com/anchor/mine/storage/AndroidStorage.kt#L805-L820), [`#L977-995`](file:///C:/Users/Banespire/AndroidStudioProjects/Mine/app/src/main/java/com/anchor/mine/storage/AndroidStorage.kt#L977-L995)
* **The Detonation:** `saveSoulFact` and `saveReliabilityState` use `INSERT OR REPLACE INTO` while omitting schema columns:
  - `soul_fact`: Omits `attrs`, `pinned_core`, `valid_from`, `valid_to`, `supersedes`, `source_msg_ids`, `extractor_version`, `last_confirmed_at`, `deleted_at`.
  - `reliability_state`: Omits `last_force_stop_detected`.
* **The Failure:** SQLite's `INSERT OR REPLACE` deletes the existing row before inserting the new one. Updating a fact's confidence or status silently wipes all metadata, provenance IDs, and pinned flags back to `NULL`.

### 7. Non-Singleton `DirectBootAlarmStore` Concurrency & SQLite File Locking (HIGH)
* **Location:** [`DirectBootAlarmStore.kt:20-45`](file:///C:/Users/Banespire/AndroidStudioProjects/Mine/app/src/main/java/com/anchor/mine/alarms/DirectBootAlarmStore.kt#L20-L45), [`AlarmReceiver.kt:66`](file:///C:/Users/Banespire/AndroidStudioProjects/Mine/app/src/main/java/com/anchor/mine/alarms/AlarmReceiver.kt#L66), [`BootReceiver.kt:55`](file:///C:/Users/Banespire/AndroidStudioProjects/Mine/app/src/main/java/com/anchor/mine/alarms/BootReceiver.kt#L55)
* **The Detonation:** `DirectBootAlarmStore` instantiates a brand new `DirectBootOpenHelper` on every invocation rather than maintaining a singleton connection. The database does not enable Write-Ahead Logging (WAL).
* **The Failure:** When `BootReceiver` runs `syncFromReminders()` inside an exclusive transaction while `AlarmReceiver` fires and attempts `removeAlarm()`, SQLite throws `android.database.sqlite.SQLiteDatabaseLockedException`. The exception in `AlarmReceiver` is swallowed in a catch block, leaving an orphaned alarm that rings again on every boot.

### 8. Database File Corruption During Backup Import with Live Writers (HIGH)
* **Location:** [`AndroidExportManager.kt:452-476`](file:///C:/Users/Banespire/AndroidStudioProjects/Mine/app/src/main/java/com/anchor/mine/export/AndroidExportManager.kt#L452-L476)
* **The Detonation:** `importFrom()` calls `dbHelper.close()`, replaces the database files via `copyFile(tempFile, originalFile)`, and deletes `-wal` and `-shm` files without acquiring an application-wide write lock or pausing background tasks.
* **The Failure:** If a background alarm, nudge tick, or chat stream performs a write while `copyFile` is copying bytes, raw disk pages are overwritten under an active SQLite handle, causing fatal page corruption (`SQLiteDatabaseCorruptException`).
