# Branching Analysis: Multi-Step Tool Loop Concurrency & Consecutive User Message Elimination

## Goal and invariant
- **Goal**:
  1. Eliminate consecutive `"user"` messages in `pack` when the LLM emits a tool call with empty `"reply": ""` in multi-step tool loops (`!turnComplete`).
  2. Prevent premature `markBatchAnswered(activeBatchIds)` in intermediate loops before the turn completes.
  3. Update `TurnCompletionTest.kt` to extract proposal and node IDs from `body` rather than reading `storage.savedProposals` directly, complying with `fake-model-tests/SKILL.md`.
- **Invariants**:
  - Pure Kotlin in `:core` (zero Android framework dependencies).
  - Strict alternating roles in LLM request packs: `system` -> `user` -> `assistant` -> `user` (system feedback) -> `assistant`. No consecutive `user` messages under any circumstances.
  - No empty placeholder messages persisted to `raw_message` SQLite table.
  - Outbox jobs marked answered only when the user turn has actually completed (either with a committed response, assistant reply prose, or loop limit termination).
  - Fake transport in tests reads ONLY request `body` (zero test cheating via backdoor storage inspection).

## Angles (mandatory)
- **data/schema**: No schema change; `raw_message` and `outbox` tables unaffected.
- **concurrency/lifecycle**: Guarded under existing `sendMutex.withLock`; turn state remains serialized.
- **failure paths**: If loop 2 fails or hits rate limits, outbox jobs are not prematurely marked answered.
- **user-visible behaviour**: No empty speech bubbles displayed or persisted; intermediate tool queries stay clean.
- **privacy/security**: `rawBot` in `pack` contains only aliases (`p_1`, `n_1`) generated by `ContextBuilder`, never raw UUIDs.
- **testability**: Pinned by unit test simulating 2-loop tool execution with empty initial reply.
- **blast radius**: Confined strictly to `ChatController.executeChatTurn` and `TurnCompletionTest`.
- **platform (Android 14, OEM)**: Unaffected; pure core logic.
- **model behaviour (what a real LLM would send)**: Real models (OpenAI, Anthropic, Mistral) frequently send `{"reply":"", "calls":[{"tool":"search_memory", ...}]}` on retrieval turns.

## Decision: chosen change, rejected options and why
- **Chosen**:
  1. Determine `turnComplete` first (`if (envelope.calls.isEmpty() || hasCommitted || turnErrors.isNotEmpty()) turnComplete = true`).
  2. If `turnComplete == true`: handle UI display, persistence to `raw_message`, and `markBatchAnswered` as before.
  3. If `turnComplete == false` (intermediate loop):
     - If `finalAssistantText.isNotBlank()`, update UI and persist.
     - If `finalAssistantText.isBlank()`, drop empty UI message and use `rawBot.trim()` as assistant message in `pack`.
     - Defer `markBatchAnswered` until `turnComplete` is true.
  4. In `TurnCompletionTest.kt`, extract `pMatch` and `nMatch` from `body` via regex.
- **Rejected**:
  - Always injecting a fake prose message like `"Thinking..."` into SQLite: rejected because it pollutes append-only `raw_message` history.
  - Skipping the assistant message in `pack`: rejected because strict APIs reject consecutive `user` messages.

## Pre-mortem: "it is a week later and this fix caused a bug; what was it?"
1. *Pre-mortem 1*: If `rawBot` is somehow empty, `assistantMsgForPack` is empty string which some providers reject.
   - *Mitigation*: Fall back to `rawBot.ifBlank { """{"reply":"","calls":[]}""" }`.
2. *Pre-mortem 2*: `turnComplete` calculation misses an edge case where a tool needs confirmation or time.
   - *Mitigation*: `ToolResult.Ambiguous`, `ToolResult.NeedsConfirm`, and `ToolResult.NeedsTime` already set `turnComplete = true` during `envelope.calls.forEach`.
3. *Pre-mortem 3*: If loop limit (4) is hit, `markBatchAnswered` might not be called.
   - *Mitigation*: The `if (!turnComplete && loops >= 4)` branch explicitly calls `markBatchAnswered(activeBatchIds)` and sets `turnComplete = true`.
