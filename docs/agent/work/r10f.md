### 1. Goal and Invariant Restatement
- **Goal**:
  Per `session1-remediation-spec.md` line 312 and `ROADMAP.md` line 22 (P1-B 14):
  Resolve all remaining weekday and vocabulary gaps in `DateResolver`:
  1. Abbreviated weekday names ("mon", "tue", "tues", "wed", "thu", "thur", "thurs", "fri", "sat", "sun") and compound prefixes ("on next friday", "coming friday", "this coming monday").
  2. Standalone day parts and day-part modifiers ("friday morning/afternoon/evening/night", "tomorrow morning/afternoon/evening/night", "this morning/afternoon/evening").
  3. Natural duration expressions without "in" ("half an hour", "an hour", "a minute", "in a half hour").
  4. Timezone (tz) support: integrate timezone resolution with `day_rule.timezoneId` from `Storage.getEffectiveDayRule(clock.now())`.
  5. 2am edge cases: verify and uphold that at 2:00 AM (post-midnight, pre-rollover), "tonight" resolves strictly to the upcoming night (never yesterday), "today at 7pm" resolves to the current calendar day, and "today at 1am" correctly yields `PastTime`.
  6. Ambiguity rule: "no am/pm => ask" (returns `NeedsClarification` with 2 candidate chips, and `parse()` returns `null`).
  7. Clear error on past "today": returns `DateResolution.PastTime` yielding `"That time is in the past; tell me a future time."` in `Gateway`.
  8. Prompt documentation: Update system prompt in `ChatController.kt` to clearly list accepted temporal forms.

- **Invariants**:
  - Injected clock rule: All time math uses `clock.now()` and caller-supplied `timeZone`.
  - Zero seconds and milliseconds.
  - LLM proposes / code decides: LLM passes user's exact words in `due_text`, code deterministically parses and resolves.
  - Zero guessing on ambiguous 12-hour times: "no am/pm => ask".

### 2. Hypotheses / Approaches

1. **Hypothesis A (Hardcode regexes for each distinct combination)**:
   - *Approach*: Add separate top-level regexes for every day-part and weekday permutation.
   - *Issue*: Combinatorial explosion and fragile parsing order.
   - *Kill Condition*: High maintenance burden and regex conflicts.

2. **Hypothesis B (Modular tokenization & composition)** (CHOSEN):
   - *Approach*:
     a. Expand `WEEKDAYS` map to recognize standard 3-letter and 4-letter abbreviations (`mon`, `tue`, `tues`, `wed`, `thu`, `thur`, `thurs`, `fri`, `sat`, `sun`).
     b. Expand prefix matching to handle compound prefixes (`(?:on\s+)?(?:this\s+)?(?:coming\s+|next\s+)?`).
     c. Enhance `parseTimePart` to understand day-part descriptors (`morning` -> 9:00, `afternoon` -> 14:00, `evening` -> 19:00, `night` -> 21:00) both standalone and attached to weekdays or "tomorrow"/"today".
     d. Add timezone parameter `timeZone: TimeZone = TimeZone.getDefault()` to `DateResolver` constructor and `resolve(...)`, wired from `dayRule.timezoneId` in `Gateway`.
     e. Expand duration vocabulary to handle natural phrasing (`half an hour`, `in a half hour`, `an hour`, `a minute`).
   - *Prediction*: Cleanly satisfies all P1-B 14 acceptance criteria with minimal code changes, zero breakage of existing tests, and 100% deterministic testability with injected `FakeClock` and `TimeZone`.

### 3. Comprehensive Dimensional Analysis
- **Schema & Migration**: None. Operates entirely in memory within `DateResolver` and `Gateway`.
- **Concurrency & Lifecycle**: Safe. All methods are thread-safe and stateless with respect to instance state.
- **Process Death & Reboot**: Independent of lifecycle.
- **Failure Paths**: Unrecognized text returns `DateResolution.Failed` without exceptions. Past times return `DateResolution.PastTime`. Ambiguous hours return `DateResolution.NeedsClarification`.
- **Privacy & Security**: Zero sensitive user data processed; pure temporal parsing.
- **Testability**: Highly testable across multiple simulated wall-clock times (noon, 2am, 8am, 10pm) and multiple timezones (UTC, America/New_York, Asia/Kolkata).

### 4. Pre-Mortem (3 Potential Failure Modes)
1. *Timezone drift between Calendar and SimpleDateFormat*: If `Calendar` uses injected `timeZone` but `SimpleDateFormat` uses default JVM timezone, formatted chip labels will display the wrong time.
   - *Prevention*: Set `timeZone` on every `SimpleDateFormat` instance inside `DateResolver`.
2. *Weekday abbreviation colliding with ordinary words*: e.g. "sat" colliding with verb "sat".
   - *Prevention*: Require weekday words to be anchored with prefix ("on", "this", "next", "coming") or followed by time/day-part, or match full weekday name.
3. *Past-time false positives at 2am*: Calling "tonight" at 2am could accidentally check against 2am and think 9pm yesterday is in the past.
   - *Prevention*: Explicitly test 2:00 AM clock state in unit tests, verifying that "tonight" resolves to 9:00 PM on the current day (> 2am).
