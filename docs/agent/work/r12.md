# R12 Branching Analysis: Turn Lifecycle & Confirm-Path Concurrency (A-01, A-04, A-09)

## Goal and Invariant
- **A-01 (Turn Lifecycle Cancellation)**: `handleSendMessage` `CancellationException` handler must persist `"[Interrupted]"` ONLY for this turn's active in-flight assistant bubble. It must never re-insert or corrupt an existing assistant message from a prior turn or after completion. Content must be real reply text (never "Thinking...").
- **A-04 (Confirm-Path Concurrency CAS)**: `handleConfirmChange` must atomically consume the proposal before executing any mutation. `UPDATE proposal SET status='consumed' WHERE id=? AND status='open'`. The first tap succeeds; any concurrent or subsequent tap sees 0 rows affected and receives `"Proposal already resolved"`. Exactly 1 mutation, 1 receipt, 1 reminder/node created.
- **A-09 (Paused Node Acceptance & Failure Cleanup)**: `handleConfirmChange` accepts nodes in status `"paused"` (matching `getActiveNodes` and `Resolver.resolve` candidates). On terminal failures (`"Node not found"`, `"Node is no longer active"`), the proposal is consumed so dead chips do not persist errors indefinitely. `"Invalid choice"` leaves proposal open.

## Angles (one line each, mandatory)
- **data/schema**: No schema migration required; `proposal` table already has `status TEXT` column (`'open'`, `'consumed'`). CAS uses standard `WHERE id=? AND status='open'`.
- **concurrency/lifecycle**: Eliminates check-then-act race between `getProposal` and mutations. `currentBotId` token strictly pairs with the active coroutine turn.
- **failure paths**: Terminal errors (`"Node not found"`, `"Node is no longer active"`, expired time) consume the proposal to clear dead UI state; non-terminal input error (`"Invalid choice"`) preserves the proposal.
- **user-visible behaviour**: Double-tapping a chip yields exactly one action and one receipt; subsequent taps cleanly inform "Proposal already resolved". Stopping a request before response streams leaves history clean.
- **privacy/security**: No secrets leaked; append-only `raw_message` integrity preserved without duplicate rows or PK collisions.
- **testability**: Deterministic gated fakes test cancellation before placeholder and after insert without arbitrary `delay()`. Concurrency tested with `kotlinx.coroutines.async`.
- **blast radius**: Confined to `ChatController.handleSendMessage` cancellation block, `Gateway.handleConfirmChange`, and `Storage.consumeProposalCas`.
- **platform (Android 14, OEM)**: SQLite implementation uses `SupportSQLiteStatement.executeUpdateDelete()` under `Dispatchers.IO`.
- **model behaviour (what a real LLM would send)**: Real models or users issuing rapid confirmations or stops will encounter deterministic state transitions.

## Decision: chosen change, rejected options and why
- **Chosen**:
  1. Add `suspend fun consumeProposalCas(id: String): Boolean` to `Storage` interface.
  2. In `AndroidStorage`, implement via `compileStatement("UPDATE proposal SET status = 'consumed' WHERE id = ? AND status = 'open'").executeUpdateDelete() > 0`.
  3. In `SharedFakeStorage`, implement thread-safe CAS returning `true` only if found with `status == "open"`.
  4. In `Gateway.handleConfirmChange`, perform CAS immediately after validating that `choice` is a valid option (preserving `"Invalid choice"` without consume).
  5. In `Gateway.handleConfirmChange`, allow `node.status == "paused"` alongside `"active"` and `"in_progress"`.
  6. In `ChatController`, introduce `@Volatile private var currentBotId: String? = null`. Set upon placeholder generation; clear upon `insertRawMessage` completion or drop. In `CancellationException`, persist `[Interrupted]` only if `currentBotId != null && last?.id == currentBotId && !last.content.isNullOrBlank() && last.content != "Thinking..."`. Wrap in try/catch to ensure `CancellationException` is rethrown cleanly.
- **Rejected**:
  - In-memory Mutex in `Gateway`: doesn't persist across controller instances or reflect true DB state.
  - Consuming proposal on `"Invalid choice"`: rejected because a bad argument or misread token should allow the user to select the correct chip.

## Pre-mortem: "it is a week later and this fix caused a bug; what was it?" List 3.
1. `consumeProposalCas` consumes the proposal before a subsequent validation (e.g. invalid time in payload), leaving the proposal consumed without an action. *Defense*: Time validation and choice validation happen before or explicitly handle terminal feedback.
2. `currentBotId` is not cleared when an exception other than `CancellationException` occurs, leaking into the next turn. *Defense*: Clear `currentBotId` in `finally` block or right after turn completion.
3. Multi-turn loops in `handleSendMessage` assign a new `botId` for each loop; if cancelled on loop 2, `currentBotId` must match loop 2's `botId`. *Defense*: Set `currentBotId = botId` on each loop iteration where a placeholder is emitted, and clear it when that bot message is committed or dropped.

Finish with: what input would break the fix:
- Two threads calling `consumeProposalCas` concurrently on the exact same millisecond: solved by SQLite single-writer lock and atomic `UPDATE` rowcount check.
