# Branching Analysis: Task R10c (follow_up Edge Validation, Atomic Transactions & Undo)

Date: 2026-11-04  
Status: In Progress  
Authors: Antigravity  

---

### 1. Guarantee Restatement
- **Guarantee 1 (Existence Validation)**:
  - When creating a task with a follow-up link (`follow_up_to` / `follow_up_of`), the source node must exist. If not, return `ToolResult.Error` and create nothing (no node, no reminder, no edge).
  - When adding a follow-up between two existing nodes via `AddFollowUp`, both source and destination nodes must exist in storage. If either is missing, return `ToolResult.Error` and create nothing.
- **Guarantee 2 (Atomic Creation in One Transaction)**:
  - When creating a node with an initial follow-up edge, the insertion of the node, its reminder (if any), the follow-up edge, and the corresponding raw event(s) must occur within a single database transaction.
- **Guarantee 3 (CREATE Undo Soft-Deletes Connected Edges)**:
  - When a user undoes the `CREATE` operation of a node, any follow-up edges connected to that node (both inbound `dst_id == nodeId` and outbound `src_id == nodeId`) must be soft-deleted (`deleted_at = now`) in the same database transaction that marks the node `cancelled` and removes its reminder.
- **Guarantee 4 (AddFollowUp Validation: No Self-Loop, No Duplicate, Depth-Bounded Cycle Check)**:
  - `srcNodeId == dstNodeId` is rejected as a self-loop error.
  - If an active (non-soft-deleted) edge of type `follow_up` already exists from `srcNodeId` to `dstNodeId`, it is rejected as a duplicate error.
  - If adding `srcNodeId -> dstNodeId` would create a directed cycle (i.e. `dstNodeId` can already reach `srcNodeId` along active `follow_up` edges), it is rejected as a cycle error. The reachability search is depth-bounded (max depth 20).
- **Guarantee 5 (RemoveFollowUp Validation & UNLINK Undo)**:
  - Removing a follow-up validates that the edge exists and is not already deleted; returns error if not found.
  - On removal, `before_json` stores the serialized `Edge` and `opType = "UNLINK"` is recorded.
  - Undoing `UNLINK` restores the edge with `deleted_at = null` and records `UNDO_UNLINK`. Both `AddFollowUp` and `RemoveFollowUp` produce receipts with valid undo tokens.

### 2. Diagnosis of Current Codebase

1. **`Gateway.handleCreate` does not validate source existence and executes multiple transactions**:
   In `core/src/main/java/com/anchor/core/gateway/Gateway.kt`:
   ```kotlin
   storage.createNodeAndCommit(node, event, reminder)

   if (!followUpTo.isNullOrBlank()) {
       val srcNode = storage.getNode(followUpTo)
       if (srcNode != null) {
           ...
           storage.createEdgeAndCommit(edge, edgeEvent)
       }
   }
   ```
   - If `srcNode == null`, it silently swallows the error and leaves the created node without an edge. The spec requires: *"validate source and destination exist (else Error, create nothing)"*.
   - The node is created in transaction 1 (`createNodeAndCommit`), and the edge is created in transaction 2 (`createEdgeAndCommit`). The spec requires: *"create node + reminder + edge in ONE transaction"*.

2. **Undo of `CREATE` does not touch edges**:
   In `Gateway.handleUndo`:
   ```kotlin
   if (event.opType == "CREATE") {
       val cancelledNode = currentNode.copy(status = "cancelled", closedAt = clock.now(), updatedAt = clock.now())
       val undoEvent = RawEvent(newEventId, "UNDO_CREATE", "node", currentNode.id, undoOf = token, beforeJson = afterJson, afterJson = json.encodeToString(NodeStateSnapshot(cancelledNode, null)), tsUtc = clock.now())
       val deleteRemId = currentReminder?.id ?: "r_${currentNode.id}"
       storage.updateNodeAndCommit(cancelledNode, undoEvent, deleteRemId)
       return ToolResult.Committed("UNDO", currentNode.id, "Removed: ${currentNode.title}", newEventId)
   }
   ```
   Edges pointing to or originating from `currentNode.id` remain active and non-deleted. The spec requires: *"undo of CREATE also soft-deletes the edge"*.

3. **`handleUndo` rejects `UNLINK` operations**:
   In `Gateway.handleUndo`:
   ```kotlin
   if (event.targetType == "edge") {
       if (event.opType == "LINK") {
           ...
           return ToolResult.Committed("UNDO", event.targetId, "Removed follow-up link", newEventId)
       }
       return ToolResult.Error("Undo for this edge operation not supported")
   }
   ```
   `UNLINK` cannot be undone.

4. **`ChatController` lacks validation, cycle checks, and error receipts for follow-ups**:
   In `ChatController.kt`:
   `UiAction.AddFollowUp` and `UiAction.RemoveFollowUp` directly call `storage.createEdgeAndCommit` / `deleteEdgeAndCommit` without validating source/destination existence, self-loops, duplicate edges, or cycles, and do not route through Gateway or produce error receipts.

### 3. Architecture & Fix

1. **Storage Interface & Implementations**:
   - Update `createNodeAndCommit` to accept `edge: Edge? = null, edgeEvent: RawEvent? = null`. In `AndroidStorage.kt`, insert `edge` and `edgeEvent` inside the existing `db.beginTransaction() ... db.setTransactionSuccessful()` block.
   - Update `updateNodeAndCommit` to accept `softDeleteEdgeIds: List<String> = emptyList()`. In `AndroidStorage.kt`, execute `UPDATE edge SET deleted_at = ?, updated_at = ? WHERE id = ? AND deleted_at IS NULL` for each ID inside the transaction block.
   - Mirror these updates in `SharedFakeStorage.kt`.

2. **Gateway Follow-Up Operations & Cycle Detection**:
   - In `Gateway.kt`:
     - Add `handleAddFollowUp(srcNodeId: String, dstNodeId: String, causeMsgId: String? = null): ToolResult`.
     - Add `handleRemoveFollowUp(edgeId: String, causeMsgId: String? = null): ToolResult`.
     - Implement `causesCycle(srcId: String, dstId: String, maxDepth: Int = 20): Boolean` using BFS over `storage.getEdgesForSource(..., EdgeTypes.FOLLOW_UP)`.
     - In `handleCreate`:
       - If `!followUpTo.isNullOrBlank()`: look up `storage.getNode(followUpTo)`. If null, immediately return `ToolResult.Error("Cannot create follow-up: source item '$followUpTo' not found")` without creating the node or reminder.
       - Pass `edge` and `edgeEvent` into `storage.createNodeAndCommit(node, event, reminder, edge, edgeEvent)`.
     - In `executeTool("propose_change")`: validate `followUpTo` before generating proposals or handling create.
     - In `executeTool("add_follow_up")` and `executeTool("remove_follow_up")`: wire to handlers.
     - In `handleUndo`:
       - For `event.opType == "CREATE"`: query `storage.getEdgesForDestination(currentNode.id)` and `storage.getEdgesForSource(currentNode.id)`, collect distinct IDs, and pass as `softDeleteEdgeIds` to `storage.updateNodeAndCommit`.
       - For `event.targetType == "edge"` and `event.opType == "UNLINK"`: decode `Edge` from `beforeJson`, set `deletedAt = null`, `updatedAt = clock.now()`, and restore via `storage.createEdgeAndCommit(restoredEdge, undoEvent)`.

3. **ChatController Wiring**:
   - In `ChatController.kt`:
     - `UiAction.AddFollowUp`: delegate to `gateway.handleAddFollowUp(action.srcNodeId, action.dstNodeId)`. On `ToolResult.Error`, add error `ReceiptState` to `transientReceipts`.
     - `UiAction.RemoveFollowUp`: delegate to `gateway.handleRemoveFollowUp(action.edgeId)`. On `ToolResult.Error`, add error `ReceiptState` to `transientReceipts`.
